# 複合システム設計書：Personal Trading Risk OS（作る意味だけで構成する）

作成日: 2026-08-02
前提: docs/phase0_report.md（データソース調査）、docs/xauusd_institutional_research.md（機関動向調査）の結論の上に立つ。
対象: USDJPY / XAUUSD / BTCUSD。方向予測・売買シグナルは出力しない（当初方針を維持）。

---

## 0. 設計原理：「買えないもの」だけで構成する

既製品（ATR系インジ、COTダッシュボード、ニュースフィルタEA、セッション表示等）は個々の「表示」を無料で提供している。これらのクローンを作る意味はゼロ。一方、以下の3つは**どんな製品も構造的に提供できない**：

1. **あなたの口座の実測データ** — あなたのブローカーが、あなたの取引時刻に、実際に何pips滑らせたか。製品はこのデータを持ち得ない。
2. **検証規律** — walk-forward・vintage・レジーム分割・n明記で「この統計は本物か」を判定する装置。製品は売る側の都合でこれを内蔵しない。
3. **拒否権を持つ統合** — 既製品はすべて「表示して、判断はお任せ」。データを突き合わせて**「この取引計画は統計的に成立していない」と具体的に指摘する**製品は存在しない（それは投資助言に近づくため、商品としては出せない。個人の自己使用ならば作れる——これが個人開発の唯一の構造的優位）。

さらに複合システムとしての性質：**価値が自分のデータの蓄積とともに複利で増える**。スプレッドログ・取引ログが溜まるほど判定が正確になる。既製品は何年使っても賢くならない。

## 1. 全体構成（7層）

```
L6 アイデア検死室     ← 新しい手法/インジの主張を同じ検証装置で解剖
L5 事後帰属エンジン   ← 損益を「方向スキル/コスト/ヒゲ/事故」に分解
L4 取引計画リンター   ← 計画を提出→統計チェック→pass/warn/veto ★中核
L3 執行観測所         ← 自分のブローカーのスプレッド/滑りを実測
L2 機関コンテキスト   ← COTクラウディング/流動性カレンダー/ヒゲゾーン/ベーシス
L1 条件付きボラエンジン← イベント×銘柄×レジームの実現ボラ分布 + GARCHベースライン
L0 データ・検証基盤   ← 1分足/イベントテーブル(vintage)/walk-forward装置
```

L0〜L2 は既報告の Phase 1 + 機関コンテキスト・レイヤーそのもの。新規は L3〜L6。

## 2. 各層の仕様

### L0. データ・検証基盤（Phase 1 = T1〜T3 と同一）
- 3銘柄の1分足（Binance / dukascopy-node）、イベントテーブル（ALFRED vintage + FF過去アーカイブ + FMP/JBlanked補完）、UTC統一、parquet。
- **walk-forward 検証エンジンを独立モジュールにする**（L1/L2/L6 が共用）。入力＝任意の「条件→翌期間の分布」仮説、出力＝レジーム別統計 + n + 安定性フラグ。これが全システムの品質保証装置。

### L1. 条件付きボラエンジン（Phase 1 = T4〜T5 と同一）
- イベント種別×銘柄のボラ増幅率（中央値・IQR・n）、初動反転率、GARCH(1,1)/GJR + ナイーブベースライン。
- 出力は常に**分布**（点予測しない）。「CPI後60分: ±0.42%（IQR 0.28-0.61, n=87, レジーム安定✓）」の形式。

### L2. 機関コンテキスト（xauusd_institutional_research.md 第4部と同一）
- クラウディング percentile（COT、公表時刻厳守）/ 流動性カレンダー / ヒゲリスクゾーン / ベーシス監視。
- 採用は仮説 H1〜H6 の検証通過が条件。落ちた指標は出さない。

### L3. 執行観測所（新規・自分のデータ）★買えないもの其の一
**目的**: 「コストを必ず入れる」ルールを、仮定値ではなく実測値にする。

- **収集A（インフラ不要）**: MT5/ブローカーの取引履歴を定期エクスポート→注文価格と約定価格の差（実測スリッページ）、約定時刻を取り込む。
- **収集B（要・常時稼働1プロセス）**: MT5 の tick を1秒毎に記録する最小ロガー（取引しないEA、またはPython+MT5 API）。Oracle Always Free か取引時のみ自宅PCで可。VPS前提にはしない——Bが無くても A + 業界公表値で縮退運転できる設計にする。
- **産出物**: 「自ブローカーの時刻別スプレッド曲線」「イベント別スプレッド拡大倍率（実測）」「成行スリッページの分布」。
- これがバックテストのコストパラメータに直接入る。**自分の検証が自分の執行環境と一致する**——既製品バックテスターが原理的にできないこと。

### L4. 取引計画リンター（新規・拒否権を持つ統合）★中核
**「どちらに張るか」はユーザーが決める。リンターはその計画が統計的に成立しているかだけを検査する。**

入力（Discord ボットに1行で提出）:
```
/plan XAUUSD long entry=3352 stop=3341 target=3378 size=0.5lot hold=4h
```

検査項目（すべて L0〜L3 の統計に基づく。各判定に根拠数値と n を添付）:

| # | 検査 | 使う層 | 出力例 |
|---|---|---|---|
| C1 | ストップ距離 vs 条件付き想定レンジ | L1 | 「stop幅11$は今後4hの想定レンジ(中央値14$)より狭い。ノイズだけで刈られる確率が高い」 |
| C2 | ストップ位置 vs ヒゲゾーン | L2 | 「3341は前日安値3342.1の直下=集中帯内。3338台への移動を提案」 |
| C3 | 保有時間帯 vs 流動性カレンダー | L2 | 「hold窓が21:30 CPIを跨ぐ。イベント時想定ボラは平常の3.1倍(n=87)」→ warn/veto |
| C4 | サイズ vs クラウディング調整後ボラ | L1+L2 | 「MM 82pctile週。口座リスク1%に収めるなら0.3lotが上限」 |
| C5 | コスト比率 | L3 | 「この時刻の実測スプレッド+滑り往復≒$0.9。想定利幅$26の3.5%→許容」 |
| C6 | 目標の実現可能性（方向ではなく到達幅として） | L1 | 「4hで+$26は想定レンジ分布の88pctile。時間切れ濃厚」 |

出力: **PASS / WARN(修正案付き) / VETO(禁止事項抵触: イベント跨ぎ等)**。
方向の是非は一切評価しない。「その方向観で行くならこの設計は壊れている/整っている」だけを言う。

### L5. 事後帰属エンジン（新規・自分のデータ）★買えないもの其の二
毎月、取引履歴を自動分類して**損失の解剖学**を出す:

- ヒゲ刈り死: ストップ約定後N分以内に価格がエントリー方向へ回帰した取引の割合
- コスト死: スプレッド+滑りが想定利幅のX%を超えていた取引
- 事故死: イベント/薄商い帯にストップされた取引
- 純粋な方向ミス: 上記のいずれでもない損失

→ 「あなたの先月の損失の41%はヒゲ刈りで、うち7割はリンターがwarnを出していた」という形のレポート。**改善可能な損失（設計起因）と改善不能な損失（方向起因）を分離する**。これがシステム全体の効果測定でもある：リンターの警告に従った取引と無視した取引の成績差が、システム自体の価値の実測値になる。

### L6. アイデア検死室（新規・検証規律の再利用）
新しい手法・インジ・言説（例: FVG、○○オシレーター）を試したくなったら、購入・採用の前に L0 の walk-forward 装置に掛ける標準手順。入力フォーマットを固定（条件の定義→対象期間→仮説）し、レジーム別・n付き・コスト込みで判定。
- 効果は防御的：**悪いアイデアを安く殺す**。有料インジ1本・悪い手法1つの回避で開発コストの相当部分を回収する。
- 副産物として、本プロジェクト自身の指標（H1〜H6）も同じ装置で定期再検証される（レジーム変化で死んだ指標の自動退役）。

## 3. なぜこれは「作る意味しかない」のか（層別の代替可能性）

| 層 | 既製品での代替 | 作る意味 |
|---|---|---|
| L0 検証基盤 | 汎用バックテスターはあるが vintage/レジーム分割/n強制はない | 規律の実装そのものが価値 |
| L1 ボラ分布 | ATR/GVZ等は「今のボラ」。イベント×銘柄×レジームの条件付き分布は製品に無い(JBlankedが断片のみ・厳密性なし) | 有 |
| L2 機関コンテキスト | 個々の表示は無料製品あり(COTチャート等)。percentile化+検証済みのみ通知+統合は無い | 中（表示部分は既製品併用可） |
| L3 執行観測所 | **原理的に不可能**（自分の口座のデータ） | 最大 |
| L4 リンター | **商品として存在し得ない**（助言規制との境界。表示産業は判断を返さない） | 最大 |
| L5 帰属エンジン | ジャーナルアプリは記録するが統計と接続した原因分解はしない | 大 |
| L6 検死室 | 存在しない（売る側の利益に反する） | 大 |

注: L2 の「表示」部分（COTチャート、セッション表示等）は既製品の現況調査を別途実施中であり、代替できる表示は作らず既製品を使う。本設計の新規実装は「検証・実測・判定」に集中する。

## 4. 実装順序と工数感

| 順 | 内容 | 依存 | 目安 |
|---|---|---|---|
| 1 | L0+L1（= Phase 1 そのもの。T4で停止・報告） | Phase 1 GO判断 | 最大 |
| 2 | L3収集A（取引履歴インポート） | なし。**今日から手動でも開始可** | 小 |
| 3 | L4 最小版（C1/C2/C3のみ、Discordボット） | L0+L1 | 中 |
| 4 | L2（H2/H3→H1の順で検証→通過分のみ） | L0 | 中 |
| 5 | L5（取引が溜まってから。目安50取引〜） | L3A | 小 |
| 6 | L3収集B、L6、L4残り | 上記 | 小〜中 |

- 常駐なし（cron + Discord Webhook、Phase 2 構想のまま）。全データ無料。
- **最初に価値が出るのは L3A**：実装以前に、過去の取引履歴が既にあるなら即座に帰属分析の素材になる。

## 5. 正直な限界と kill criteria

- このシステムは方向のエッジを作らない。方向判断が長期的に無価値なら、システムは「それを数字で早く教えてくれる」だけ（L5 がその判定装置になる——これも価値ではある）。
- L1 の検証（T4）で綺麗な関係が出なければ、リンターの C1/C6 は GARCH/ATRベースラインに縮退する。それでも C2〜C5 は独立に機能する＝**一点賭けの設計ではない**。
- L2 の各指標は検証未通過なら出さない。「思ったより関係がない」も正式な結論として採用する。
- 停止条件文化は維持：Phase 1 GO が出るまで L0/L1 は着工しない。L3A のみ、データ収集の性質上（過去は取り戻せない）先行開始を推奨する。
